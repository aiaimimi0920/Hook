# 社区参与方式

[English](./contributing.md) · [文档中心](../README.md) · [工程贡献规范](../../CONTRIBUTING.md)

欢迎从一次问题反馈、一处文案修正或一个使用示例开始，让 Otter 更好用。
不写代码，也能参与；需要修改实现时，再按工程贡献规范准备开发环境和验证。

## 选择一种参与方式

| 想做什么 | 从哪里开始 |
| --- | --- |
| 反馈问题 | 先搜索[已有 Issues](https://github.com/aiaimimi0920/Otter/issues)，没有相同问题时[新建 Issue](https://github.com/aiaimimi0920/Otter/issues/new)，附上版本、环境和复现步骤。 |
| 提出功能建议 | 说明实际场景、目前怎么完成、哪里不方便，以及希望得到什么结果。涉及 Loom 能力时，注明所需的能力和连接条件。 |
| 分享使用经验 | 在 Issue 中介绍一个可复现的截图、标注或节点处理示例，用脱敏图片说明操作和结果，并注明所需版本与能力。 |
| 改进文案或文档 | 指出具体页面、原文、建议文字及理由；直接提 Issue，或修改对应文档后提交 PR。参见[翻译教程](./translating.zh-CN.md)与[文案与文档](#文案与文档)。 |
| 贡献代码 | 先阅读[工程贡献规范](../../CONTRIBUTING.md)和[项目目录](../architecture/overview.md#2-repository-layout)，再进行范围明确的修改和相关验证。 |

## 让问题更容易复现

一份清楚的反馈可以包含：

1. Otter 版本或提交、使用的发布包名称，以及 Windows 版本。
2. 从什么状态开始、按什么顺序操作、预期结果和实际结果。
3. 与问题有关的环境：例如显示器数量与缩放、HDR 状态、源程序名称；不相关的项目可以省略。
4. 涉及 OCR、翻译或投射时，补充 Loom 版本、相关能力是否安装并启用、连接和授权状态。
5. 最小示例、脱敏截图或必要的日志片段，并说明哪些步骤已经验证、哪些还无法验证。

实时截图捕获的是程序或屏幕区域的像素，浏览器滚动或切换标签会改变画面。
[实时截图范围](../features/LIVE_CAPTURE.md)和[投射说明](../features/QR_PROJECTION.md)可帮助区分功能边界与异常。
请不要仅凭接收计数、解码计数或一张截图宣称显示帧率或性能提升；相关证据边界见
[LiveRelay 诊断](../features/LIVE_RELAY_DIAGNOSTICS.md)。

只修正错字时，修改对应语言即可；功能含义、限制或操作步骤发生变化时，请同步已有的中英文对应内容。
界面措辞建议应附上控件位置或操作路径，不要假定 Otter 使用与其他项目相同的语言文件结构。

保留命令、配置项、快捷键、协议标识符、下载文件名和链接的准确写法。
翻译链接文字与图片说明时，不要改变实际目标或夸大功能；标题调整后检查页内锚点。
不要移除平台限制、能力安装及授权要求、签名状态或验证边界；许可证正文和第三方声明保持完整。

新指南放入 `docs/` 下适合的主题位置，并在文档中心添加入口。
优先补充已有说明，避免为同一功能维护多份相互矛盾的规则；不为整理目录随意移动既有文档。

## 提交改进

1. 搜索相关 Issue 或 PR，确认问题和改动范围；较大调整先说明方案，减少重复工作。
2. 从当前代码建立自己的工作分支，只修改与该问题相关的文件。
3. 文档改动检查链接、图片、标题锚点、代码示例和中英文一致性；代码改动遵循[工程验证要求](../development/ENGINEERING.md#6-tests-and-verification)。
4. 在 PR 中说明改了什么、为什么、执行了哪些检查，以及尚未验证的部分。截图展示实际结果，不把模拟演示当作原生验收证据。

提交建议或 PR 不代表已经合并、发布或支持全部设备与场景；以维护者评审和相关验证结果为准。

## 分享前检查隐私与授权

公开 Issue 和 PR 可能被任何人阅读。分享前请移除截图中的私密内容，以及日志中的凭据、令牌、个人路径和其他不必要的个人信息。
只上传你有权公开的素材；不要附带他人的私人画面、未授权素材或可直接使用的配对信息。

疑似安全漏洞请遵循[安全反馈流程](../../SECURITY.md#reporting-a-vulnerability)，不要公开利用细节或敏感材料。
如果私密报告入口不可用，按该安全策略仅提交请求建立私密沟通渠道的最简 Issue。
