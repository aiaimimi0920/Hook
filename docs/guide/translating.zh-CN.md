# 参与 Otter 翻译

[English](./translating.md) · [社区参与方式](./contributing.zh-CN.md) · [文档中心](../README.md)

欢迎校对中英文介绍、翻译使用说明，或提出更清楚的界面措辞。
可以从一句话开始，不需要先搭建 Windows 开发环境。
本文介绍的是 Otter 项目文案与文档的翻译，不是对截图执行 OCR 或翻译的操作教程。

## 先提交一条建议

在[已有 Issues](https://github.com/aiaimimi0920/Otter/issues)中搜索相关讨论。
没有相同建议时，可以[新建 Issue](https://github.com/aiaimimi0920/Otter/issues/new)，写明：

- 目标语言、文档链接或界面位置；
- 原文、建议译文，以及修改理由；
- 必要的上下文或复现路径；界面截图请先移除私密内容。

例如：说明某个按钮是“重新执行”还是“仅显示已有结果”，比只说“翻译不自然”更容易判断。
不确定实际行为时，请把疑问写出来，不要在译文中补出尚未确认的功能。

当前核对到的界面文字直接保存在组件与选项目录等源码中，不能通过仿照其他项目新增一个语言文件就完成界面翻译。
界面文字修改属于代码修改，应定位实际调用位置，按[工程贡献规范](../../CONTRIBUTING.md)验证。
文档有中英文版本不代表应用已经提供对应的界面语言切换。

## 修改一篇文档

1. 先读完整段落和对应功能说明，确认文字描述的是当前行为。
2. 在自己的工作分支上修改对应 Markdown 文件；小改动也可以通过 GitHub 文件编辑器提出 PR。
3. 如果只是某种语言的错字，修改该语言即可；功能含义或步骤变化时，同步已有的对应语言版本。
4. 新增整篇译文前，先说明语言与范围，确认目标文件名和入口。新译文放在相同主题目录，并添加互相可用的语言链接和文档索引入口。
5. 预览排版，检查链接、标题锚点、图片说明、表格和代码示例，然后提交 PR，列出修改范围和未验证的部分。

这条文档路径不要求运行原生截图程序；涉及界面或原生行为的改动，再遵循相应工程检查。
不要把没有运行的检查写成通过，也不要把文案修正当作功能验收。

## 翻译时保留什么

- 保留 Otter、Loom、Art 等产品和协议名称的准确写法。
- 保留命令、代码、配置键、快捷键、文件名、URL 目标和协议标识符；链接显示文字可以翻译。
- 在源码文案中保留插值表达式、占位符和转义；不要改动枚举值、动作标识或逻辑条件来完成文字翻译。
- 保留平台与兼容性限制、能力安装及授权要求、签名状态和验证边界。
- 标题变化后更新对应页内链接；让可见按钮文案、提示与无障碍标签表达一致的操作。
- 保留许可证原文和第三方归属声明。机器辅助翻译仍需结合使用场景校对。

## 想增加完整的界面语言

先通过 Issue 讨论范围与方案：文字来源、语言选择与默认值、格式化与占位符、字体布局、无障碍标签，以及如何验证。
这需要实现与验证语言机制，不能仅凭翻译几处字符串宣称已支持一种新语言。
Otter 设置中的翻译目标语言用于内容翻译，不应被当作界面语言注册入口。

发布截图、日志或示例前，移除私密内容与凭据；安全问题遵循[安全反馈流程](../../SECURITY.md#reporting-a-vulnerability)。
