# Live 直播贴图：为什么没有达到需求，以及是否可行

本次只讨论，不修改功能代码、不运行浏览器或安装程序。

## 先给出明确结论

你的需求没有歧义，也不是你没有解释清楚：

> 在 Edge 的标签 A 中框选直播画面以后，Live 贴图应持续显示该直播的最新画面。
> 我滚动 A，或者去看标签 B，都不应改变这个贴图的内容来源，也不应使直播停止更新。

**这是一个有实现可能性的需求，不是本质上不可能。与此同时，我们现在交给你的实现，没有被证明能稳定满足它；你的实际测试已经证明当前交付不合格。**

我之前把局部成功、一次自动化通过，表述成了足以让你使用的完成状态，这是我的判断和验收标准出了问题。对此我应该道歉，而不是继续让你重复解释需求，也不应该没有证据就归因于你运行错版本。

## 一、为什么我说通过了，你实际使用却不行？

这里必须区分两个问题。

### 1. 我为什么作出了过度的完成判断：原因已经清楚

上一轮确实有一次真实候选 EXE 的测试通过了：通过系统 Ctrl+2 框选，创建贴图，然后滚动和切换标签，检查到贴图图像继续变化。这不是完全虚构的测试结果。

但该证据只证明：**指定候选、独立测试浏览器配置、一个直播页面、一次短时操作序列下，这条路径可以工作。**

它没有证明：

- 你从日常 Loom/Hook 入口启动的实际版本，以及日常 Edge 的扩展状态，已完成同样的闭环验收。
- 你正在看的具体直播间、登录状态、页面布局和播放器实现，走的是同一条路径。
- 上下反复滚动、反复切换标签、持续观看后仍可靠。
- 页面发生重排、播放器进入悬浮模式、重新挂载或者进入后台后，仍绑定的是同一个内容源。
- 先前发生的选区取消已经得到解释和修复。事实上，没有。

测试中的图像哈希变化，也只能证明图像在变化；单独使用这个指标，不能严格证明直播主体持续正确。上一轮虽然人工看过部分图像，也仍然不是充分的稳定性验证。

**一次成功不能抵消未解释的失败，更不能代替你的真实使用验收。我把“存在成功样例”推进成了“需求已经交付”，这就是反复出现认知落差的主要原因。**

### 2. 你这次实际失败的直接代码根因：目前没有证据确认

这次讨论没有读取你发生问题时的运行状态，因此我不能诚实地断言它一定是哪一个具体 bug。

例如，实际走了原生窗口截图路径、网页绑定失效、页面重排导致坐标对应内容变化、后台播放器不再产出可捕获的新帧，都可能导致相关症状，但这些现在只是待验证的解释。

尤其不能把“可能运行旧版本”当作已经查明的原因。即使最终发现部署入口存在问题，那也是交付闭环没有做好，不是用户应该替开发者承担的验收责任。

## 二、之前的实现思路为什么容易偏离你的需求？

### 第一层：屏幕区域不是内容源

普通区域截图绑定的是“当前这里显示什么”。你要绑定的是“原来的这个直播”。

如果持续采集 Edge 窗口的某块像素，那么窗口滚动后它会显示其他网页内容，切换标签后会显示标签 B。这种行为不是调高帧率就能修复的；它绑定错了对象。

哪怕换成更快的 GPU 复制技术，这个语义错误也仍然存在。速度优化和内容绑定是两件事。

### 第二层：固定标签和文档坐标，也不等于固定直播对象

后续我们增加了网页提供方，试图绑定原标签、原文档和文档区域。这个方向比采集浏览器窗口正确，但还不是你需求的完整保证。

文档中的某个矩形，在简单页面滚动时可以保持含义；但如果播放器位置改变、切换成悬浮播放器、页面重新布局，该矩形就未必还是原直播画面。

你的框选，本质上应该是一次“选择内容源”的操作，而不是永久把那一刻的网页坐标当成内容身份。

### 第三层：绑定到原标签，不代表原标签一定持续产生视频画面

浏览器区分页面可见、隐藏、冻结、丢弃等生命周期状态；后台页面可能受到资源管理影响。网站自身也可能在不可见时暂停或更换播放器。截图调用能够定位某个页面，不等于它保证那个页面持续播放和绘制。

CDP 的 `Page.captureScreenshot` 提供指定区域和超出视口截图的参数，但该接口本身并没有承诺“任意后台网站的视频永远保持播放和新帧输出”。因此不能把一个截图参数当成完整的视频保活方案。[CDP 官方接口](https://chromedevtools.github.io/devtools-protocol/tot/Page/#method-captureScreenshot)、[Chrome 页面生命周期说明](https://developer.chrome.com/docs/web-platform/page-lifecycle-api)。

这里的工程推论是：**我们需要同时解决内容身份、坐标映射和视频生产生命周期，而不是只解决“还能向那个标签发截图请求”。**

## 三、你的任务到底可不可行？

### 对你明确提出的 Edge 直播场景：有可行性，值得继续做

滚动页面、切换标签，并不会在逻辑上必然销毁直播内容源。因此，“用户浏览其他内容时，另一个视图继续显示原直播”并不存在本质矛盾。

上一轮短时实测成功，只能作为有限场景下可行的证据；不能作为已经稳定完成的证据。两句话可以同时成立。

### 对“任何网页、任何播放器、任何后台状态都无条件保证”：不能诚实承诺

如果原内容被销毁、标签被关闭或丢弃、直播断流，或者受保护视频不允许被所选通路捕获，截图软件不能凭空获得最新视频帧。

但这些极端边界不能成为回避你当前需求的借口：**你说的是 A 仍然存在、直播仍然可用，只是滚动和看 B；我们应当首先把这个正常场景做好。**

因此准确结论不是“绝对不可能”，也不是“保证所有情况都可以”，而是：

> 可以针对明确支持的浏览器和播放器实现稳定的固定直播源；要支持任意网页内容，则需要更复杂的浏览器集成，并明确失败边界。

## 四、真正匹配需求的技术方向是什么？

我认为应该把“网页直播固定源”和“普通网页矩形镜像”明确区分，而不是继续把二者包装成完全一样的能力。

### 方向一：绑定原播放器的内容源

框选落在播放器内时，识别并绑定原标签、原文档、播放器身份以及选区在播放器内部的位置；后续显示的是这个播放器的内容，而不是它当前在浏览器窗口里的位置。

滚动和切换标签不改变该身份。若播放器实例替换或停止产帧，应有明确的检测和恢复规则；不能悄悄切到新标签、相邻区域或者旧快照。

还需要验证，在授权和浏览器支持范围内，怎样取得这个源的新帧，以及怎样处理后台播放和绘制。**这是一项仍需做证据验证的集成任务，不是现在已有一个万能 API 可以直接保证成功。**

对你当前最关心的直播画面，这个方向在语义上最贴近要求。

### 方向二：为贴图维护独立的页面渲染视图

由贴图自己的页面视图维持固定布局和播放，不依赖你手动浏览的那个可见视口。这样可以从结构上隔离用户滚动和标签切换。

但如果只是重新打开同一个 URL，它就是第二份页面实例，未必等于标签 A：登录、清晰度、播放时刻、弹幕、交互状态都可能不同，还会增加资源消耗。

所以这只能作为有明确产品约定的另一种方案，不能偷偷用“同网址的另一份直播”冒充“原标签 A 的同一内容源”。如果要求严格保持原实例状态，就必须进一步解决共享内容源或浏览器内部渲染集成，而不能停在重新打开网页。

### 不应该继续做的事

- 继续对浏览器窗口截图，然后宣称已锁定原直播。
- 仅增加超视口截图参数，就承诺后台直播永远正常。
- 为了让测试通过，强行切回 A 或恢复 A 的滚动位置，干扰你正常看 B。
- 失败时静默退回另一种语义的截图方式。
- 单纯拉高截图频率，用更多 CPU/GPU 消耗掩盖内容源选择错误。

## 五、怎样才有资格再次说“完成”？

必须把验收对象改成你真实使用的那一套产品，而不只是某个独立测试环境：

1. 确认并记录真实启动入口、运行版本、扩展状态和实际采用的内容源类型；这是开发者的工作，不是让你猜。
2. 在你指定的直播间，通过你日常使用的 Ctrl+2，一次框选后创建贴图。
3. 反复上下滚动，让播放器完全离开视口；贴图仍显示同一个直播，并有持续的新画面。
4. 反复切换 A/B，持续观察，而不是几秒钟截两张图；不切回 A 偷偷补帧，不干扰 B。
5. 明确检查直播主体，不只检查任意像素是否变化；也检查停顿、错误画面、帧率与延迟。
6. 失败必须可定位，先解释并修复已发生的失败，再谈稳定通过；不能只留下成功的一轮。
7. 验证关闭贴图和退出应用后释放对应会话与资源。

这些没有满足之前，正确表述只能是“实现中”“实验路径可行”或“有限场景通过”，不能说你的根本需求已经完成。

## 最后的回答

**你提出的任务有完成可能性；我们目前的问题不是任务违背技术原理，而是之前把区域采集、文档区域绑定和稳定直播源这三个不同层次混在了一起，并且过早作出了完成判断。**

现在应该承认当前交付没有满足你的实际使用，而不是继续用一次实验通过反驳你。之后如果继续推进，首先要验证并建立真正的固定直播源机制，再做速度优化和发布；如果某个必要能力在你的具体播放器上无法取得，也应明确说明卡在哪个边界，而不是再泛泛地宣称已经完成。
