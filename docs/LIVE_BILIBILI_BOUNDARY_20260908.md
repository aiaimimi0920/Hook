# B 站直播 Live 贴图：真实原因与当前未完成边界

## 直接结论

**你的需求没有被当前普通 Ctrl+2 实现。我之前把另一条网页入口的验收当成了
你日常框选功能的完成，这个结论不成立。不是你的操作方式需要为这个缺口负责。**

这里必须区分两件事：

- **现有窗口像素截图路线无法独立满足这个要求。** 它的输入只有浏览器窗口当前
  输出的像素和窗口内坐标，没有直播间标签页、文档或视频对象身份；滚动或切换标签
  之后，输入画面已经变了。提高 FPS、更换 GPU 拷贝或保留上一帧都不能还原原直播。
- **你的需求并非技术上不可能。** 本次已经用本机 Edge 打开真实 B 站直播页面，
  在原区域滚出视口和原标签页隐藏之后，仍读到了持续变化的原直播画面。
  因此现在不能把问题归咎于“B 站一定禁止”“所有视频都无法后台捕获”或微软 API 限制。

**本轮没有完成产品修复，也没有生成一个声称已修复的新版 EXE。** 本轮产出是
可复跑的真实直播诊断和修正后的验收边界，不是又一次用测试脚本代替产品交付。

## 1. 当前代码的失败边界

普通入口实际走的是：

```text
Ctrl+2
  -> Rust live_capture 全局快捷键
  -> 原生框选
  -> windowId + windowRegion + rect
  -> native Live backend
  -> 浏览器窗口当前显示的像素
```

相应代码：

- `src-tauri/src/native/app_runtime.rs` 的 `live_capture` 分支进入原生截图模式。
- `src/hooks/useSelection.ts` 的 Live 确认只传入窗口和矩形信息。
- `src/services/appLiveCaptureBackend.ts` 只有收到 `browserGrantId`、
  `browserSelection` 或 `browserAuthorization` 才选择 browser backend；否则是 native。
- `src/services/browserLiveImport.ts` 中的网页授权及导入仍是独立命令。
- Loom 的 `capability-packages/browser-live/extension/documentBinding.ts` 才持有
  固定文档身份和文档区域；原生 Ctrl+2 不会自动走到它。

所以，**如果这张贴图是直接用普通 Ctrl+2 创建的，你描述的现象符合当前实现，
不是偶发的截图延迟。** 若使用的是专用网页入口，仍需核对实际运行版本、扩展启用
及该会话的提供方，不能仅凭相同现象断言它也是同一原因。本次没有读取你的私人
浏览器标签或宣称确认了你那张贴图的会话类型。

## 2. 这次确实测了 B 站视频，而非绿色测试网页

独立、未登录的 Edge profile 中打开公开页面：
[B 站直播间 6](https://live.bilibili.com/6)。测试时该页面的同源子框架中有正在
播放的 1280×720 视频。它不是纯 HTML 时钟、截图回放或从播放器地址另拉的流。

诊断脚本：`scripts/tests/bilibili-video-boundary-probe.ts`。
本次结果：`artifacts/bilibili-video-boundary-20260908-r1/summary.json`。

检查了两条采样手段：

1. 持有该页面的 CDP target，使用当前网页提供方相同的
   `Page.captureScreenshot` 固定文档裁剪参数；不随激活标签重新找目标。
2. 持有原 `<video>` 元素，使用 canvas 读取它的已解码帧，作为诊断对照。

第二条**没有安装进产品**，也不是建议未经验证地再更换一次捕获架构。
本次第一条已经能取到直播画面，优先应修复实际入口和目标绑定，而非先重写 GPU 管线。

| 阶段 | 确认的真实状态 | 两次视频时间，单位秒 | 图像检查 |
| --- | --- | --- | --- |
| 初始 | 视频正常播放，文档可见 | 18.786 → 21.061 | 两次解码帧、文档裁剪哈希均变化 |
| 滚出视口 | `scrollY=856`，原裁剪区域底部为 `-199.75` | 23.287 → 25.533 | 仍为原直播内容，非黑帧；两次哈希均变化 |

每张 320×180 解码对照帧都有超过 57,000 个非黑像素，且时间和图像均变化。

不同，说明不是保留旧截图冒充更新。

- [滚动后的原直播裁剪](../artifacts/bilibili-video-boundary-20260908-r1/scrolled-2-document.png)
- [切换标签后的原直播裁剪](../artifacts/bilibili-video-boundary-20260908-r1/hidden-2-document.png)

这些证据只证明**这个公开房间在此次 Edge 环境下的捕获原语可行**。它们不是：

- 用户指定直播间的复现；本轮尚未收到具体房间链接和实际创建入口的回复。
- 普通 Ctrl+2 → 安装扩展 → Hook Live Unit 的端到端验收。
- 30/60 FPS、多路、长时间播放、登录状态、受保护视频或所有 B 站播放器的保证。
- 全程物理鼠标滚轮验收；最终诊断使用实际页面 `scrollTo`，并断言区域已离开视口。

早期 CLI 探针中，滚轮未改变 `scrollY`，另一次新页面激活没有使源文档变为 hidden。
这两次没有记为滚动或切换标签通过。最终脚本使用单个独立 Edge profile 的真实
标签，并要求 `document.hidden=true` 才采集隐藏阶段。

## 3. 真正修好还缺什么

不是继续“加快现有截图”就能完成。产品链必须让用户的框选实际变成：

```text
用户在原直播间选择区域
  -> 浏览器明确授权的原标签/文档身份 + 原文档区域
  -> Hook 创建使用该提供方的 Live Unit
  -> 滚动和切换标签只改变源窗口显示，不改变 Live 的目标
```

其中还没有完成的是普通入口与上述浏览器身份/授权流程的集成，以及该入口在真实
安装版本中的验收。不能把 native HWND 当作 tab ID，不能失败后静默回退到窗口截图，
也不能强制把用户的原页面滚回去或抢回原标签来制造成功。

浏览器扩展的 `activeTab` 授权有自己的用户操作边界，不能把现有 Hook 全局快捷键
直接当作已经获得浏览器授权。可以改变产品入口和权限交互，但要明确实现，不是
靠另一条隐藏命令自动等价。[Chrome activeTab 文档](https://developer.chrome.com/docs/extensions/develop/concepts/activeTab)

未来验收必须从用户实际使用的创建入口开始，确认会话使用 browser provider，
然后在真实 B 站直播中滚出播放器、切换标签，检查 Hook 贴图内的直播像素继续变化。
还应覆盖源标签关闭、插件退出、贴图关闭后的释放，以及多个区域共享源时的负载。
