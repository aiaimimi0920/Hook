# Live 截图四项问题：当前事实与处理边界

## 1. 失败却没有原因提示

这是已定位的前端缺口，不是用户操作问题。

- 启动失败原先只对七类资源/数量拒绝显示提示；其他异常直接返回，用户只能看到截图没有产生。
- 运行中原生状态变为 `failed` 时，controller 停止轮询，但没有显示失败通知。
- IPC 读取失败原先只把内部状态设为 `recovering`，没有对用户说明正在重试。

本次修改补齐安全的未知启动失败提示、终态失败提示和恢复提示，复用现有通知样式，不重新增加 LIVE 标签或贴图工具栏。持续同一种故障只通知一次；恢复成功后再次失败可以重新提示。关闭贴图和 controller 销毁会清理通知去重状态。原始错误中的网页内容、路径等不直接显示。

涉及 `liveCaptureAdmissionFeedback.ts`、`liveCaptureStatusFeedback.ts`、`liveCaptureController.ts` 和 `useSelection.ts`；测试覆盖未知启动失败、源关闭终态、持续轮询失败去重与恢复后的再次提示。具体构建与验证状态见 V0.2.24 的 `VALIDATION.md`，不能以源代码通过替代已安装版本验收。

## 2. 滚动网页后保持原来的内容区域

**当前产品没有实现。** 当前 Ctrl+2 绑定的是“浏览器窗口中的像素区域”，不是“文档中的内容区域”。滚动改变了该窗口区域里的像素，所以当前 Live 会跟着改变。

要实现用户要求，绑定对象应包含页面身份以及文档坐标或稳定元素身份。采集必须向该页面请求原区域内容，而不能继续读取当前屏幕上的同一块矩形，也不能通过偷偷滚回原位置影响用户浏览。

此前隔离 CDP 原型只证明了自有测试网页中固定文档区域在滚动后的截图与更新；没有接入 Hook 的真实贴图、浏览器授权或 Loom 的可信能力包。原型通过不等于产品能力已经交付。

## 3. 切换 tab 后保持原来的页面

**当前产品同样没有实现。** 浏览器 HWND 通常没有随着 tab 切换而变化，仅绑定 HWND 无法区别页面 A 和页面 B。

这需要稳定绑定原始 browser target/tab 和文档身份，并明确处理页面导航、关闭、权限撤销和进程重启。页面身份失效时应停止并解释原因，不能静默变成另一个 tab。要保证跨滚动和跨 tab，两项能力必须同时具备；仅拿到 tab 视频流不能自动解决文档区域随滚动改变的问题。

产品接入应通过 Loom 已验证的 browser capability package；Hook 消费受约束的会话和帧，不把 browser target 假装成 Win32 windowId，不绕过安装、授权、撤销和资源限制。是否接受安装浏览器扩展已向用户询问；本次没有擅自安装扩展、读取现有浏览器 profile 或开启调试端口。

普通 DOM 区域是合理的首个验收对象。后台视频、DRM、跨域 iframe、虚拟列表、导航后的页面以及依赖真实用户手势的按钮都需要分别验证，不能承诺任意网页区域都与前台保持完全相同的行为和帧率。

## 4. 同网页多个分割区域仍然卡顿

### 判断

**共享实现目前只完成了采集源复用，没有完成共享呈现。仍存在明确的线性开销，但当前还没有足够性能证据证明哪一项是整机卡顿的主因。**

同 HWND、进程和尺寸的多个裁剪确实共享一个 WGC pool；已有专项测试证明六个裁剪只有一个源采集池。不能把“还卡顿”直接等同于“没有共享源”。但也不能把“只有一个源池”当成性能问题已经解决。

现有路径是：

```text
一个 WGC 源纹理
  -> 裁剪 A 的独立纹理 -> A 的交换链 -> Present
  -> 裁剪 B 的独立纹理 -> B 的交换链 -> Present
  -> 裁剪 C 的独立纹理 -> C 的交换链 -> Present
```

每个到期裁剪仍执行源纹理到裁剪纹理的 GPU copy，随后执行裁剪纹理到交换链的 copy 和独立呈现。共享源回调持有订阅锁执行这些裁剪提交；单一 compositor 又串行处理各贴图的呈现。此外，每张贴图仍有状态、轮询、帧邮箱和回退职责。

因此开销更接近“一个源的采集成本 + 所有可见裁剪的处理/呈现成本”，而不是“只截一次，所以增加贴图没有额外成本”。多个重叠区域、多个放大的贴图，仍可能让总呈现像素量远大于网页本身。

### 下一步优化的证据门槛

1. 在真实运行的 EXE 上记录同源池数、可见裁剪数、总裁剪像素量、共享回调耗时、GPU 提交 busy、present busy、CPU 回退次数，区分负载来源。
2. 对同一个网页做 1/2/4/6 个裁剪对照，并保持总裁剪面积近似相等，再单独增加总面积，避免混淆“数量成本”和“像素成本”。
3. 根据实测决定是否改成共享帧/共享呈现表面、批量提交或进一步减少独立拷贝，而不是只调低固定数量限制。
4. 不能直接在共享回调中释放订阅锁后继续访问订阅：目前锁也保护删除、GPU slot 释放和旧回调隔离，必须先补生命周期证明。
5. 不能简单丢弃 GPU busy 时的最后一帧：静态网页的一次性更新可能没有后续帧来替换它。
6. 准入模型目前还保守地对每个裁剪重复预留完整源成本。这会偏早拒绝新贴图，但不是已证明的实际 VRAM 用量；只放宽账目不会修复卡顿，反而可能放大负载。

本次没有将这些候选优化写成“已经完成”，也没有降低安全保护或替换已验证的订阅生命周期。
