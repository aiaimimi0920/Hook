# 无需用户安装扩展的 Live 方案讨论

有其他办法。按照你现在明确的产品要求，不能继续把“用户手动安装浏览器扩展”
作为默认前提。我之前选择的方案解决了部分采集技术问题，却增加了你没有接受
的使用门槛。这里仅讨论路线，不实施代码或浏览器配置变更。

需要同时说清楚：不安装扩展可以做到；对于任意已经打开的第三方程序，在不
改变其运行方式、不要求任何配合的条件下，永久显示已离开视口的原区域并继续
实时交互，目前没有一条我能据实承诺全面可靠的通用方案。

## 为什么换一种截图 API 仍不足以解决

窗口采集得到的是窗口产生的画面。Windows.Graphics.Capture 的公开采集对象
是显示器或应用窗口，并没有“任意应用中的某个历史控件/网页元素”这样的接口。
参见 [微软窗口采集说明](https://learn.microsoft.com/en-us/windows/uwp/audio-video-camera/screen-capture)。

浏览器滚动后可能不再绘制原位置，切换标签后也可能停止合成或降低后台内容
更新。即使更快地复制 GPU 纹理，也不能保证拿到源程序没有继续产生的新帧。
保留旧纹理只能留下旧画面。要稳定更新，需要原内容继续拥有可采集的呈现来源，
或者接入能够提供该内容的程序内部能力。这是对采集边界的工程判断。

## 方案一：由 Hook 管理独立网页实例

Hook 自己管理网页运行环境。用户可以在 Hook 中打开网页并框选；技术依赖由
产品安装和启动流程承担，不要求用户给日常浏览器安装扩展。原浏览器可以正常
滚动、切换标签，Hook 内的页面实例独立运行。

这个方向有完成可能性，适合形成稳定的“网页 Live”产品能力，但必须承认它的
语义：独立打开的网页拥有自己的状态。原页面上的登录、临时输入、播放器进度、
WebSocket 会话等不能仅凭同一个 URL 自动复制过去。点击独立实例中的按钮，
也不能声称是在操纵原 tab 的同一个控件。

如果从日常浏览器 Ctrl+2 一次框选就自动接管，还需要可靠取得 URL、识别选区、
恢复页面状态并确认内容相同。这些都是额外工作，不能藏在“自动复制网页”这个
说法里。对登录态或复杂业务页面，可能仍需要一次明确的打开或登录操作。

因此，它能消除安装扩展的步骤，但不能直接当作你要求的任意原程序控件分身。

## 方案二：对视频利用浏览器自带画中画

对你目前最关注的直播视频，可以优先研究浏览器内置画中画。Edge 已有原生
画中画功能，把视频放入独立浮动窗口供用户在其他页面或应用中继续观看。
参见 [Edge 官方介绍](https://blogs.windows.com/msedgedev/2025/06/06/debuting-new-enhanced-controls-for-picture-in-picture-in-microsoft-edge/)。

可研究由 Hook 协调这个浏览器原生能力，再把实际视频窗口作为 Live 内容源。
这里有希望保持原视频会话，也不用复制登录态或重新打开直播间。

但这目前是待验证的方向：如何无扩展稳定触发、如何消除多余的浏览器浮窗、
如何映射选中的视频内部区域、如何支持多路及保留播放器交互，都不能预先承诺。
它主要适用于视频，不能覆盖任意网页按钮、聊天区和普通应用 UI。网页提供的
Document Picture-in-Picture 也需要网页侧调用，不能自动赋予外部截图工具
抓取任意页面元素的权限。
参见 [Chrome 对 Document Picture-in-Picture 的说明](https://developer.chrome.com/docs/web-platform/document-picture-in-picture)。

## 方案三：浏览器或应用适配，用户侧不安装扩展

可以为不同程序实现内部适配，统一暴露为 Hook 的 Ctrl+2 操作。浏览器调试
协议、应用自有接口、受支持的独立视图都可能成为接入方式。这样可以追求统一
交互，同时接受内部存在多种实现和明确的支持范围。

问题在于，普通日常浏览器通常没有现成开启的调试入口。Edge 官方调试流程
要求使用远程调试参数启动，必要时使用独立 profile。仅说“改用 CDP”不能
消除启动与接入条件，也不应偷偷关闭用户浏览器或修改其启动方式。
参见 [Edge DevTools Protocol 文档](https://learn.microsoft.com/en-us/microsoft-edge/devtools/protocol/)。

直接向程序注入、拦截渲染调用也不是可以保证通用的捷径：目标不绘制原内容时，
拦截仍没有新帧；不同渲染框架、版本和进程边界还需要分别处理。当前不应再把
这样一个研究方向包装成已经可交付的通用实现。

## 我对路线的建议

先将“无需用户安装扩展”确定为产品约束，同时区分两个目标：

- 若必须保留日常浏览器中原直播的同一会话，优先做内置画中画接入的最小验证，
  验证成功也只先承诺视频场景，不将其冒充任意 UI 的通用方案。
- 若可以接受由 Hook 持有独立网页，管理网页实例更适合作为无扩展的网页功能
  主线；需要明确接受独立会话与原页面状态不同的取舍。

如果两种取舍都不接受，而且必须覆盖任意原程序、任意区域、无需程序配合，
我现在不能提供一个已验证可行的完整实现方案。应先做兼容性与能力边界验证，
不要再让你经历先宣称完成、实际使用却落回普通窗口截图的过程。
